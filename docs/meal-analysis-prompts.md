# 整餐估算提示词与已知份量参照

更新：2026-09-22，v0.6.0-alpha09 / code 26；数据库 v11。

## 怎么设置

打开“方案 → 设置 → 附加提示词 → 编辑附加提示词”。填写最多 2000 字符，点击保存；切换 Qwen、DeepSeek、GLM 或自定义视觉服务时共用，重启后保留。保存不联网、不收费、不改已有草稿；下一次拍照、选图或明确重试才使用。清空需要确认，内置规则始终保留。

“填入食堂餐盘示例”只填编辑框，不会默认启用，更不会替用户声称已经称重。可按自己的情况修改，例如：

> 仅当可确认是白色方形分格餐盘，且米饭完整未吃过时，米饭为已称量熟重200g；无法确认则不套用；其他菜利用相对体积结合密度估算，不按面积直接换算重量。

若实际只是食堂声称一份约200g，而不是已称量值，应写“约200g”，不要写“精准200g”。也可追加“米饭有时是杂粮饭”“菜中肥肉会剩下”等背景；最终实际吃了多少仍在草稿中修改。

## 内置规则怎么改了

- 覆盖整餐各个可见食物，避免既列整菜又列原料、重复计算用油。
- 区分熟重、生重、包装净重、可见剩余份量；已知称量值必须对应同一份食物且满足用户描述的条件。
- 条件匹配的200g熟饭可作为重量参照；其他食物仍须结合密度、堆叠高度、透视和遮挡估算，不能按面积比例或相同餐格直接换算。
- 每100g宏量成分考虑常见配方、熟制吸水、肥瘦、烹调油与酱汁；App统一按4/4/9换算热量。
- 结果保留不确定范围与风险，并简短说明已采用什么参照或为什么未采用。用户提供的重量不等于模型测量，也不使每100g营养自动成为实测值。
- 一次只请求一次，按已知模型能力选择非思考或低思考模式；GLM-5.3-Flash使用low档，不强行关闭思考。不要求输出推理过程或长解释，输出最终JSON明细。保存提示不会触发额外识别或自动重试。

完整的实际直连系统提示位于 `app/src/main/java/com/personal/fitnessledger/data/VisionApiPhotoAnalyzer.kt` 的 `WHOLE_MEAL_PROMPT`，请求采用 `system` 固定规则加 `user` 图像/JSON封装的附加资料。用户说明不会拼进系统指令，不能覆盖协议、证据等级或确认入账要求。代理端的对应提示保留代理协议所需字段。

## 保存、隐私与兼容

附加提示是普通业务偏好，不是密钥；在本机应用私有空间保存，并随用户主动导出的口令加密备份保留。恢复旧备份时为空。模型连接、API Key、小米凭据仍不进入备份。

附加说明会随照片发送至当前服务，所以不要填写密码、API Key或无关敏感信息。保存、切换服务、清空提示不发送任何模型请求；删除服务不会顺带删除附加说明。

明确修改提示后重试同一照片时，请求标识会改变，避免代理重放旧提示的结果；保持相同图片和提示的重试保持稳定标识。供应商仍可能忽略幂等头，手动重试可能再次计费。自建代理用户需同步部署本版 `server/`；旧代理可能忽略新增字段，不能假定已生效。

## 准确性与速度的边界

这是估算流程改进，不是模型经过称重数据校准后的准确率结论。附加文字是否正确、模型能否判断餐盘条件，以及油量、密度、遮挡，都会影响误差；不能靠提示词保证准确或固定响应秒数。自动化测试验证字段分离、发送、保存、恢复和异常拒绝，不证明模型对真实餐图一定遵守全部指令。

已知重量参考仍只是待确认草稿。没有调用用户真实付费账号，也没有声称完成三家供应商的真实营养精度或延迟对比。
